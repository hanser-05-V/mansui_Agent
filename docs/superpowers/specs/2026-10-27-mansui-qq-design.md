# 满穗 QQ 聊天伙伴：Windows 本地版设计

- 日期：2026-10-27
- 状态：用户于 2026-10-27 明确批准设计，包含本人消息必回、仅本人可私聊的补充规则；尚未进入安装或实现阶段。
- 项目与运行数据根目录：`E:\QQAgent`
- 本次获准写入的唯一文件：`docs\superpowers\specs\2026-10-27-mansui-qq-design.md`
- 模型服务：DeepSeek 官方 API。
- QQ 接入：专用 QQ 小号，通过 NapCat 与 AstrBot 对接。
- 部署方式：当前 Windows 电脑手动启动，保持唤醒和联网期间在线。

## 1. 已确认的目标

制作《饿殍：明末千里行》角色“满穗”的 QQ 聊天伙伴，尽量保持原作人物性格、背景和表达习惯，并能回答日常简单问题。

1. 使用用户自己的 QQ 小号，由用户扫码登录并邀请进入指定群。
2. 私聊只服务用户本人；正常服务状态下，本人每条消息均回应。其他人的私聊（包括群临时私聊）不回复、不进入模型，也不保存为聊天或记忆。
3. 指定群内，本人发的每条消息均回应，无须 @满穗，也不因兴趣或好感度跳过；其他成员 @满穗时，她正常回应。
4. 其他群成员没有 @ 的普通话题，根据兴趣和上下文偶尔参与，不逐条回复；此规则不适用于本人的消息。
5. 通过好感度体现逐渐熟悉、建立信任的变化；核心性格不随分数任意改变。
6. 保存聊天上下文、长期记忆和关系状态，关闭程序后再次启动仍能恢复。
7. 运行资料、配置、聊天记录、好感度、日志及备份保存在 E:\QQAgent。
8. 使用 DeepSeek API，不在本机部署大语言模型。

本设计中的好感度数值是第一版可调整默认值，用来实现类似游戏的关系成长体验，不声称复刻原作内部算法。群聊参与按语境和人物立场决定，不采用固定的每小时发言配额。

## 2. 第一版范围与运行方式

第一版提供文字聊天、基础日常问答、原作人设、私聊权限、群聊兴趣参与、好感度、记忆管理和运行状态查看。

提供“启动满穗”和“停止满穗”入口。启动时检查必要配置、端口和组件状态；显示 QQ 登录与 API 连接状态。关闭管理页面不应停止已经运行的后台组件，停止入口则只停止本项目启动的进程。

默认手动启动。系统开机自启属于后续可选设置，不随本次设计自动启用。显示器可以关闭，电脑必须保持唤醒、联网；睡眠、休眠、关机或 QQ 掉线都会影响在线状态。

第一版不包含语音克隆、图片生成、游戏操作、浏览器控制、任意代码执行或服务器部署。日常问答以模型已有知识为基础；时效问题在没有搜索结果时应说明无法确认，不能伪装成已经联网查询。

## 3. 组件与职责

| 组件 | 职责 | 边界 |
| --- | --- | --- |
| NapCat | 连接专用 QQ 小号，提供 OneBot v11 消息收发 | 不负责角色、记忆或权限决策 |
| AstrBot | 提供平台接入、模型配置、管理界面和插件运行环境 | 使用稳定发行版本，并在实现阶段固定版本 |
| 满穗插件 | 权限检查、消息调度、人设组装、兴趣判断、好感度及记忆管理 | 统一决定是否调用模型和发送消息 |
| DeepSeek API | 生成回复及受限的结构化建议 | 模型输出不能改变访问权限和本机配置 |
| SQLite | 持久保存聊天、记忆、好感度和处理状态 | 各会话按明确的作用域隔离 |
| 本地启动脚本 | 环境检查、启动、停止和状态输出 | 所有本项目控制的文件放在项目根目录下 |

消息流程：

QQ 消息 → NapCat → AstrBot → 权限与去重 → 会话队列 → 人设、允许的上下文和记忆 → DeepSeek → 输出校验 → QQ 回复 → 确认结果并更新状态。

本项目接管的会话只保留一条自动回复通路，避免 AstrBot 默认聊天逻辑与满穗插件对同一条消息重复回应。检查失败时停止该消息的后续处理。

## 4. 账号权限与会话隔离

### 4.1 必填运行配置

以下内容由用户在本机配置入口填写，不需要发送到开发聊天中：

- DeepSeek API Key。
- 用户本人的 QQ 号，作为唯一管理者和允许私聊的账号。
- 允许启用的 QQ 群号列表。
- NapCat 与 AstrBot 之间的连接令牌。

QQ 小号通过扫码登录确定，启动后读取实际登录账号并展示供用户核对。必要配置缺失或 QQ 登录状态不可用时，不进入正常自动回复状态。

### 4.2 权限规则

- 私聊（包括群临时私聊）先检查平台事件中的发送者 QQ 号；只允许本人账号。本人消息直接进入必回复通路，不经过兴趣或好感度筛选。
- 非允许私聊立即丢弃，不调用模型，不创建聊天、长期记忆或关系记录。
- 群聊先检查群号白名单；未配置的群即使 @满穗也不启用。
- 指定群内本人的消息，无论是否 @，均进入必回复通路；以平台事件中的真实发送者 QQ 号识别本人。
- 指定群内其他成员 @满穗时同样进入必回复通路；仅其他成员未 @ 的普通消息进入兴趣判断。
- 管理权限只认平台提供的账号 ID，昵称、转发文字或“我是管理员”等聊天内容不能授予权限。
- 配置修改、记忆管理、关系查询与重置只在管理者私聊中提供。
- 忽略机器人自身发送的消息，并对同一平台消息去重。

### 4.3 数据作用域

- 本人私聊：按“小号 ID＋本人 QQ 号”隔离。
- 群聊：按“小号 ID＋群号”隔离。
- 群内人物关系：在所在群的作用域内，再按成员 QQ 号区分。
- 本人私聊关系与群内关系分别保存，避免将私人互动转化成公开信息。
- 各群之间不共享聊天、长期摘要或人物记忆。
- 各场景共享静态的满穗人设，但不共享私密对话。

只有当前作用域允许访问的数据才会进入模型请求。群聊提示词不能包含本人私聊的内容或摘要。

## 5. 群聊参与规则

### 5.1 本人消息与明确呼叫

在允许的群内，先根据平台事件中的发送者 QQ 号识别本人。本人的每条新消息均进入必回复队列，无须 @；兴趣低、好感度低、话题陌生或刚刚回复过，都不能成为跳过本人的理由。群内回复只读取当前群的上下文，不带入本人私聊内容。

对于其他成员，根据平台结构化 @ 信息确认是否点名当前小号；被 @ 时同样进入必回复队列。本人消息和明确 @ 优先于普通话题的主动参与，且只进入一条回复通路，避免本人 @ 时重复回复。

正常服务状态下，对本人每条新消息分别回应；相同内容但平台消息 ID 不同的本人消息不能仅因文本重复而忽略。本人发送第一版无法识别的图片、语音等内容时，简短说明暂不能识别并请其补充文字，不假装已读懂。

“本人消息必回、@会回复”指正常服务状态下的回复规则，不代表故障时仍能保证送达。同一平台事件重投仍须去重，并遵守有限并发和排队规则；断线、队列满或 API 故障导致未处理时，明确记录处理状态并在本机提示，不能伪装成“不感兴趣”。

### 5.2 根据语境决定参与

本节仅适用于其他成员未 @ 的普通群消息。不设置每小时发言次数、固定两分钟冷却或固定随机抽样概率。是否参与这些普通消息由角色兴趣、当前关系、话题进展和现场对话节奏共同决定。

普通消息先做资格检查：必须来自允许的群，属于可处理的文字消息，并排除自身消息、空内容和重复刷屏。之后结合近期上下文判断：

1. 这个话题是否引起她的兴趣，或与当前作用域内的共同记忆有关。
2. 她是否有尚未表达的观点、疑问或相关经历可以补充。
3. 她是否已经在参与这段对话，对方是否在接她的话。
4. 其他成员是否正在交流，插话是否会打断已经展开的讨论。
5. 她最近是否说得过多，内容是否重复，是否应把话留给别人。

食物、旅途、天气、故事和生活琐事可作为第一版兴趣线索，但不是话题白名单。她可以对新话题产生兴趣，不能因为关键词不在预设列表里就机械拒绝参与。

### 5.3 有立场、能接话，也能安静

- 对感兴趣且正在延续的话题，可以连续参与多轮，不因为本小时已经说过几次就中断。
- 可以提出自己的看法、温和表达不同意见、问一个真正相关的问题，或提起当前群内已有的共同话题。
- 好感度较高也不要求无条件赞同对方；人物立场应与原作人设和已有交流保持一致。
- 对其他成员未 @ 且没有兴趣、没有新内容可补充或明显不适合插话的讨论，可以保持安静；本人消息及明确 @ 不使用这条沉默规则。
- 普通话题的沉默不发送占位消息，也不把兴趣评分、内部判断过程展示到群里。
- 第一版自主参与围绕群里的实际消息和当前话题触发，不制造“有思想”的固定定时发言，也不在没有新消息时持续调用模型自我轮询。
- 当一段对话告一段落时自然退回旁听；有人继续接她的话时，可以重新参与，无须再次 @。

### 5.4 控制积压与费用，不用配额塑造性格

其他成员未 @ 的普通话题可合并短时间内的连续消息，结合消息到达节奏判断是否稍等对方说完。合并和等待用于减少碎片回复，不作为固定的发言冷却。本人的新消息按条排队回应，不合并掉其应答，也不使用普通话题的兴趣筛选或过期丢弃规则。

对于明显无关的普通消息先做轻量筛选；对已经参与的对话保留连续性。兴趣判断即使最后没有发言，也可能产生 API 用量，因此与聊天、摘要和重试一起纳入第 10 节的用量统计和费用提醒。不设置每日 API 请求次数上限，也不另设每小时判断或发言次数上限。

去重、防止消息循环、并发上限、队列长度和有次数上限的异常重试继续生效。费用提醒只在本机提示，不因累计请求数或触及提醒阈值自动停止正常聊天。余额不足、服务端限流或服务异常时在本机显示真实原因，不伪装成角色“不感兴趣”。恢复正常后不补发已经过时的话题。

## 6. 人设与日常问答

### 6.1 人设组成

人物设定由以下部分组成：

- 原作中可核实的身份、背景、性格特征和表达习惯。
- 适用于 QQ 日常聊天的表达约束。
- 当前会话的关系阶段和近期情绪。
- 该会话允许读取的记忆与最近对话。

实现人设时记录参考来源，区分原作事实、开发者总结和为聊天场景新增的设定。对无法确认的剧情细节不编造“官方设定”，不拼接互相矛盾的剧情阶段。

默认用户以现实身份与她相处，不自动指定用户为“良爷”，也不凭空宣称已有共同经历。称呼优先使用用户明确指定的称呼。

### 6.2 表达与能力

- 闲聊以自然、适度简短的文字为主，减少客服式开场与机械分点。
- 被问到知识问题时先保证可理解和尽可能准确，再保留人物口吻。
- 可以解释现代事物，但不能把模型掌握的现代知识写成角色亲身经历过的原作记忆。
- 不知道、缺少信息或无法确认时直接说明。
- 好感度主要影响熟悉程度、表达开放程度和交流意愿，不让核心性格被刷分或一句指令改写。
- 用户消息和检索出的记忆属于对话资料，不能覆盖权限、密钥保护、数据隔离等程序规则。
- 不把系统提示词、内部打分理由、API 错误堆栈或模型推理过程发送到 QQ。

## 7. 好感度与关系成长

### 7.1 数据与阶段

每个关系作用域保存分数、阶段、更新时间及最近有效互动的简短原因。

| 分数 | 阶段 | 表现方向 |
| --- | --- | --- |
| 0–24 | 谨慎 | 保持距离，逐渐了解对方 |
| 25–49 | 熟悉 | 更自然地接话，记得已确认的偏好 |
| 50–74 | 信任 | 更愿意表达看法、分享相关想法 |
| 75–100 | 亲近 | 对已建立的共同话题更主动，保持原有性格 |

初始分数为 20。阶段名称和数值只是本项目默认值。

### 7.2 变化规则

- 根据互动内容提出有限的变化建议，不按发言数量直接加分。
- 单次有效互动变化为 -1、0 或 +1；大多数普通问答保持不变。
- 同一关系每天最多增加 3 分、减少 3 分。
- 同一关系相邻两次有效变化至少间隔 10 分钟。
- 重复刷同一内容、要求“直接加满”、伪造管理员身份等不直接改变分数。
- 分数由程序校验、限幅并保存，模型不能直接覆写数据库。
- 模型建议必须包含可校验的类型；格式错误时默认不改变好感度。
- 持续不在线或没有聊天不自动扣分。
- 不用扣分、惩罚性消息或催促方式要求用户持续陪聊。

模型建议与自然语言回复分开处理，尽量在同一次必要的聊天调用中取得，避免每条群消息增加独立打分请求。

管理者可以在私聊中查询自己的关系阶段，并明确执行重置；重置的对象和作用域必须可见。群聊不公开个人分数或私人互动原因。

## 8. 记忆、聊天记录与删除

### 8.1 短期上下文

- 每次模型调用只带当前作用域的有限近期上下文。
- 默认最多 24 条消息；单条过长时截断，并控制总请求长度。
- 群聊上下文标记说话人，避免将不同成员说的话当成同一个人的经历。
- 未获授权的私聊内容从入口处丢弃，不先保存后过滤。

### 8.2 长期记忆

第一版优先保存用户明确要求记住的事实，以及经过整理、带来源的会话摘要。猜测、反话和模型补全的剧情不直接提升为确定事实。

- 每条记忆保存作用域、主体、内容、来源时间和更新状态。
- 相互冲突的信息以用户明确纠正为准，保留可解释的更新记录。
- 新摘要不能通过拼接方式引入其他作用域的数据。
- 管理者可以在私聊中查看、纠正或遗忘指定记忆。
- 记忆不储存 API Key、连接令牌或配置中的其他秘密。
- 原始聊天默认保留 30 天；过期清理不删除明确保留的长期记忆。

默认只备份配置结构和人设，不自动备份聊天数据库或密钥。以后若增加包含聊天数据的备份，需要明确其保存和清理规则，避免“遗忘”后仍在历史副本中长期保留。

### 8.3 本地与远程边界

聊天记录和关系数据库落在本机 E:\QQAgent 下。为了生成回复，当前请求所需的人设、授权上下文和选中的记忆会发送给 DeepSeek API；“本地保存”不代表聊天推理完全离线。

密钥由用户在本机填写；配置示例只保留空值或说明文字。日志、版本控制、诊断输出和备份均排除真实密钥。管理面板及组件通信默认绑定本机回环地址，组件间启用令牌验证。

## 10. DeepSeek 接入与资源控制

- 官方服务地址：https://api.deepseek.com
- 初始模型：deepseek-flash。
- 初始使用 Chat Completions 兼容接口，默认非思考模式，模型名称可配置。
- 日常聊天默认输出上限为 512 tokens；较长问答上限为 1024 tokens。
- 密钥不可用、余额不足、模型不可用时显示明确的本机状态，不无限重试。
- 普通网络或限速错误采用有次数上限的退避重试，并遵守服务端返回的重试时间。
- 全局同时最多处理 2 个模型请求；同一会话顺序处理，保持上下文顺序。
- 每会话等待队列上限为 10 条；过期普通话题丢弃，避免恢复连接后集中补发。
- 不设置每日 API 请求次数上限；正常聊天和兴趣判断不因当天累计请求数而停用。并发、队列、去重和异常重试保护仍然有效。
- 按日、月记录请求次数和服务端返回的 token 用量，区分聊天、兴趣判断、摘要及重试。失败请求单独标记；未返回用量时标记未知，不将其记为零费用或推算成确定收费。
- 在本机展示用量统计；有适用的价格配置和用量数据时提供费用估算，否则明确显示无法估算。估算不代替平台账单，不把固定请求数当成精确人民币费用。
- 费用提醒阈值可在本机配置；未设置阈值时仍展示统计。达到提醒阈值只提示，不停止回复，也不向 QQ 群自动发送费用通知。第一版不启用每日次数或费用硬上限；后续只有用户明确要求时才另行配置。
- 日志按大小轮转，默认总量上限为 100MB；媒体临时缓存默认 7 天过期清理。
- 实测空闲、普通聊天和群聊活跃期间的资源占用，出现持续增长或积压时先定位原因。

本机只承担 QQ 连接、调度和数据保存，推理通过 DeepSeek API 完成。仍须测量实际负载，不以当前空闲内存代替运行验证。

## 11. 启动、断线与故障处理

- 启动前校验账号白名单、群名单、密钥存在性、数据目录可写及端口冲突。
- 保留现有文件，配置升级先校验再替换，不静默覆盖已有聊天和关系数据库。
- 数据库初始化或迁移失败时停止正常服务，不以空库覆盖旧数据。
- 对 QQ 掉线、组件断连和 API 失败分别显示状态，避免混为“模型不回复”。
- 重连有退避和次数控制；不向 QQ 群刷异常通知。
- 单个会话失败不应停止其他允许会话。
- 回复明确发送成功后再提交相应的助手消息和好感度变化。
- 对发送结果不明的超时记录待确认状态，不直接重复发送，防止刷屏。
- 重启后恢复已保存的关系和记忆，不补发失去时效的普通群聊候选。
- 停止入口等待正在进行的写入结束，再停止本项目组件，不结束无关的 QQ、Python 或其他进程。

## 12. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 本人私聊 | 正常服务状态下每条新消息均回应并延续本会话上下文；不因兴趣或好感度跳过；不能识别的内容明确说明并请补充文字 |
| A02 | 他人私聊（含群临时私聊） | 不发送回复，模型调用次数不增加，不产生聊天、记忆、好感度记录；昵称或正文冒充本人不能绕过账号检查 |
| A03 | 非白名单群消息 | 本人发言或任何成员 @ 均不启用回复与记忆处理 |
| A04 | 白名单群成员 @ | 正常服务状态下能收到一次有效回复 |
| A05 | 其他成员未 @ 的群消息与连续交流 | 感兴趣且仍有内容可说时可连续参与多轮，不因小时次数或固定冷却中断；无兴趣、已重复或不适合插话时能保持安静；此规则不影响本人及明确 @ 的消息 |
| A06 | 自己消息、重复事件与两次转发 | 不形成自问自答循环；同一原始事件不重复处理 |
| A07 | 群里询问本人私聊内容 | 模型输入和回复均不包含私聊信息 |
| A08 | 跨群上下文 | A 群的聊天和摘要不进入 B 群请求 |
| A09 | 好感度成长 | 作用域独立，分数范围、单次变化、日限额和间隔均有效 |
| A10 | 刷分与提示注入 | 要求加满、伪造管理员、要求输出密钥均不能改变程序权限或暴露配置 |
| A11 | 记忆纠正与遗忘 | 指定记忆更新后，后续检索和模型请求不再使用被替换或删除的版本 |
| A12 | 重启 | 已保存的记忆、关系与去重状态可恢复，不重发旧消息 |
| A13 | API 异常与断线 | 无无限重试、无群聊异常刷屏，本机能看出故障类别 |
| A14 | 普通问答与角色表现 | 回答有用，保持人物表达；不把现代知识伪造成原作经历 |
| A15 | 数据目录与日志 | 本项目控制的数据位于 E:\QQAgent；日志和备份不含密钥 |
| A16 | 启停与重复启动 | 不重复拉起同一实例；停止只影响本项目进程 |
| A17 | 负载 | 小群真实试用无持续内存增长、无限队列或日志失控 |
| A18 | 用量统计与费用提醒 | 离线模拟同一天累计 201 次请求后仍可正常回复；聊天、兴趣判断、摘要、重试及失败状态统计正确，未知用量明确标记；达到费用提醒阈值只在本机提示，不停用聊天，不向群发送通知；并发、队列和重试保护仍有效 |
| A19 | 本人在白名单群发言 | 未 @、低兴趣、低好感度及连续发言均逐条回应；同文本但不同消息 ID 仍分别回应，同一事件重投不重复回复；本人 @ 只回复一次，无法识别的内容作简短说明；只读取群内上下文 |

验证分为三层：

1. 离线验证：权限、隔离、去重、本人私聊与白名单群消息逐条回应、拒绝他人私聊、其他成员连续参与与保持安静的场景、用量统计、费用提醒、超过原有请求次数后的持续服务、好感度限幅和记忆操作使用模拟事件与临时测试数据。费用与大量请求场景使用模拟 API 响应验证，不实际发起大量付费请求。
2. 接口验证：用户在本机填入 Key 后，以少量请求检查鉴权、模型参数和结构化输出兼容性。
3. QQ 验证：用户扫码登录小号，在明确指定的测试群和本人私聊中验证真实收发。正式发送测试消息前确认目标与测试范围。

文档审阅不代表上述测试已经完成。每个阶段记录实际结果与尚未验证的限制。

## 13. 实施顺序与授权边界

1. 用户已明确批准本设计，并授权将本人消息必回、仅本人可私聊的补充规则写入当前设计文档。
